## 1. Executive Summary

| 항목 | 내용 |
|------|------|
| **KPI** | 배달 ETA 단축 & 배차 안정성 향상 |
| **메인 문제** | Kitchen Delay (식당 조리 지연) |
| **보조 문제** | 라이더 콜사(배차 공백), 악천후 수급 붕괴 |
| **근본 문제** | 배달 계약업체 의존도 → 플랫폼 협상력·품질 통제 약화 |
| **데이터 전략** | 시뮬레이션(메인) + 외부 공개데이터(파라미터 현실 근거) 병행 |
| **분석 차별점** | CS 실무 경험에서 문제 발굴 → 정량 가설 수립 → 시뮬레이션으로 검증 |

> **⚠️ 전제 명시**: 본 분석은 실데이터가 없는 포트폴리오 프로젝트다.  
> 시뮬레이션 파라미터는 CS 업무 경험 + 외부 공개데이터 기반이며,  
> "만약 이런 패턴이 실데이터에서 발견된다면 무엇을 알 수 있는가"를 분석 프레임으로 삼는다.

## 2. 시장 현황 및 도메인 이해

### 2-1. 활용 외부 공개데이터 및 파라미터 매핑

| 데이터 출처 | 활용 목적 | 뒷받침하는 파라미터 |
|------------|----------|------------------|
| 공정거래위원회 | 배달앱 시장 규모·성장 추이 | 시장 규모 배경 서술 |
| 모바일인덱스, 와이즈앱 | 플랫폼별 점유율 비교 | 배민의 시장 지위 근거 |
| 통계청, 고용노동부 | 배달 종사자 수, 콜 수 현황 | 라이더 공급 파라미터 규모 검증 |
| DoorDash / Uber Eats 논문 | ETA가 핵심 경쟁지표임을 외부 사례로 입증 | ETA 분석 방향의 근거 |
| 기상청 공공데이터 | 강수량·풍속 분포 | 악천후 등급 기준, 날씨 파라미터 |
| 배민 기술 블로그 | Kitchen 운영, 배차 알고리즘 언급 | 조리시간 파라미터 방향 참고 |

> **활용 원칙**: 외부 데이터는 시뮬레이션 파라미터의 "현실 근거"로 사용한다.  
> 시뮬레이션 결과 자체를 외부 데이터로 검증하는 것이 아니라,  
> 파라미터 설정 근거를 외부 데이터로 정당화하는 방식이다.

### 2-2. 도메인 구조 이해

배달의민족은 **3자 플랫폼(Tri-sided Platform)** 구조다.

```
고객(User) ──주문──▶ 플랫폼(Baemin) ──배차──▶ 라이더(Rider)
                         │
                    ◀──수락── 식당(Restaurant)
```

**핵심 흐름**: 주문 생성 → 식당 수락 → 조리 → 픽업 대기 → 라이더 배차 → 픽업 → 배달 완료

### 2-3. ERD 기반 도메인 테이블 구조

> **출처 명시**: ERD는 erdcloud.com의 학습용 클론 ERD (이호석 작성, 12개 테이블)를 도메인 이해 목적으로 활용한다.  
> 분석용 OLTP 스키마는 이 ERD를 **참고하되 별도 설계**한다 (상세 → 5장).

**ERD 핵심 테이블 (도메인 이해용)**

| 테이블 | 역할 | 분석 관련성 |
|-------|------|-----------|
| Users | 고객 마스터 | 수요 분석 기반 |
| Stores | 가맹점 마스터 | Kitchen Delay 분석 핵심 |
| Orders | 주문 거래 | 주문량·시간대 분석 |
| Menu / MenuOption | 메뉴 구조 | 카테고리별 조리시간 추정 |
| Carts | 장바구니 (주문 전 행위) | 전환율·주문 패턴 보조 |
| Reviews | 리뷰 | 서비스 품질 간접 지표 |
| Coupons | 쿠폰 | 프로모션 효과 분석 보조 |

> **ERD의 한계**: 배달원(Rider) 테이블이 없음. 라이더 데이터는 분석용 스키마에서 독자 설계.

### 2-4. DW 관점 테이블 분류 (데이터 파이프라인 설계 근거)

| 테이블 유형 | 대상 테이블 예시 | DW 적재 전략 |
|-----------|----------------|------------|
| **원장성 (Master)** | user_master, restaurant_master, rider_master | 시계열 적재 + 선분이력 구축 |
| **거래성 (Transactional)** | order_transaction, delivery_log, payment_transaction | 1:1 적재, 날짜 파티셔닝 |
| **양면성 (Duplicity)** | restaurant_application, rider_contract | 점이력 구축, 업무 환경별 검토 |
| **이력 (History)** | user_address_history, restaurant_status_history | 선분/점이력 방식 확정 후 시계열 조회 최적화 |

## 3. 문제 정의 (3층 구조)

```
┌─────────────────────────────────────────┐
│  [표면 문제]  배달 ETA 지연              │
│               ↓                         │
│  [운영 문제]  Kitchen Delay (메인)       │
│               + 라이더 콜사              │  ← CS 경험으로 직접 관찰
│               + 악천후 수급 붕괴          │
│               ↓                         │
│  [구조 문제]  배달 계약업체 의존도        │
│               → 협상력 약화              │
│               → 품질 통제 불가           │
│               → 수급 안정성 저하         │
└─────────────────────────────────────────┘
```

**Kitchen Delay를 메인으로 선정한 이유**

1. CS 문의 토픽으로 외부 가시성이 가장 높음 (고객 체감 직결)
2. "정성 CS 데이터 → 정량 가설 → 데이터 검증" 스토리가 자연스러움
3. 식당 단위 개입 vs 플랫폼 단위 개입으로 솔루션이 명확히 분기됨

> ⚠️ **검토 결과 — 순서 논리 보완 필요**  
> "Kitchen Delay가 ETA의 가장 큰 구성요소"라는 주장은 현재 CS 경험에 근거한 가정이다.  
> 이를 분석 전제로 삼기 전에, **mart_eta_decomposition에서 ETA 구성요소를 먼저 분해 검증**해야  
> 논리적 순서가 맞다. → 6장 파이프라인에서 순서 반영.

## 4. 가설 수립 및 측정 지표

### 4-1. 문제 1: Kitchen Delay

| 가설 | 내용 | 주요 식당 유형 | 측정 지표 |
|------|------|------------|---------|
| **A. 오버수락** | 식당이 처리 가능량보다 무리하게 수락 | 한식, 피자 (조리시간 긴 유형) | 오버수락률 = 동시 처리 주문 수 / max_capacity |
| **B. 피크 집중** | 같은 시간대 주문 폭주로 구조적 지연 | 치킨, 분식 (주문이 몰리는 구조) | Slot Congestion Index = 특정 시간 슬롯 내 주문 수 |

**솔루션 방향 분기**

```
가설 A 확인 → 식당 단 개입 (수락 제한 / 점주 실시간 알림)
가설 B 확인 → 플랫폼 단 개입 (수요 분산 / 예약 배달 유도)
```

**CS 경험 기반 파라미터**

| 식당 유형 | 평균 조리시간 | 피크 집중도 | 연결 가설 |
|---------|------------|-----------|---------|
| 한식 | 25–35분 | 중간 | 가설 A |
| 피자 | 20–30분 | 중간 | 가설 A |
| 치킨 | 15–20분 | 매우 높음 | 가설 B |
| 분식/기타 | 10–15분 | 높음 | 가설 B |

> ⚠️ **검토 결과 — 임계값 근거 명시 필요**  
> Slot Congestion Index에서 "시간 슬롯 기준(10분)"과 "임계 주문 수(N건)"의 설정 근거가 CS 경험이라면  
> 이를 문서에 명시하고, 분석 시 임계값 민감도 검증(sensitivity test)을 수행해야 한다.

### 4-2. 문제 2: 라이더 콜사 (배차 거절)

> **용어 정의**: '콜사(콜 사절)'= 라이더가 배차 요청(콜)을 거절하는 행위.  
> 콜사 발생 시 재배차 지연 → ETA 직접 증가.

| 가설 | 내용 | 측정 지표 |
|------|------|---------|
| **A. Dead Zone** | 배달 완료 좌표가 다음 콜 수요 밀집지와 멀어 고립 | Post-delivery Cold Zone Rate (좌표 기반) |
| **B. 타이트한 콜** | 완료-다음 콜 간격이 너무 짧아 체감 여유 없음 | 완료 후 콜 요청까지 소요 시간 |
| **C. 수수료 구조** | 한집배달 인센티브가 콜사 비용보다 낮음 | 콜사율 × 배달유형 × 수수료 구간 교차분석 |
| **D. 피로도** | 연속 배달 N건 이후 콜사율 급증 | 연속 배달 수(consecutive_deliveries) vs 콜사율 |

> ⚠️ **검토 결과 — 가설 우선순위 로직 필요**  
> 4개 가설이 동시에 맞을 수 있으므로, EDA 단계에서 각 요인별 콜사율 상관관계를 먼저 탐색하고,  
> 가장 설명력이 높은 요인을 중심으로 심층 분석한다. (피처 중요도로 판단)

### 4-3. 문제 3: 악천후 수급 불균형

| 가설 | 내용 | 측정 지표 |
|------|------|---------|
| **A. 콜사율 급등** | 악천후 강도↑ → 콜사율↑ | 날씨 등급별 콜사율 |
| **B. Kitchen 동반 악화** | 악천후 시 주문 폭증 → Kitchen Delay도 악화 | 날씨 등급 × Kitchen Wait Time |
| **C. 프로모션 효과** | 현재 할증 금액이 수락률에 실제 효과가 있는가 | 수락률 예측 모델 → 피처 중요도 |

**악천후 파라미터 (CS 경험 기반 보수적 추정)**

| 날씨 등급 | 주문량 배수 | 라이더 공급 배수 | 수급 Gap | CS 문의 체감 |
|---------|-----------|----------------|---------|-----------|
| 맑음 | 1.0 | 1.0 | 0 | 기준 |
| 흐림 | 1.1 | 0.95 | −0.15 | 소폭 증가 |
| 비 | 1.3 | 0.75 | −0.55 | 증가 |
| 폭우/눈 | 1.5 | 0.5 | −1.0 | 체감 3배 |

> **보정 근거**: 주문량 1.5배는 CS 경험상 보수적 추정. 실데이터 확보 시 재검증 필요.  
> 기상청 강수량·풍속 공공데이터로 날씨 등급 구분 기준을 수치화할 것.

**프로모션 수락률 예측 모델 피처**

```
[입력 피처]
날씨 강도, 배달 거리, 완료 후 콜 밀도, 할증 금액,
연속 배달 수, 시간대, 배달 유형 (한집/알뜰)

[출력]
수락률 (0~1) → 피처 중요도 도출 → 프로모션 설계 근거
```

## 5. 데이터 전략

### 5-1. 전략 원칙

```
시뮬레이션만 사용 → "만든 데이터" 비판 → 신뢰도 부족
외부 공개데이터로 파라미터 근거 확보 → 시뮬레이션 신뢰도 보완
```

 본 분석은 시뮬레이션 데이터로 가설 검증 구조를 설계하고,  
> 분석가로서 "어떤 질문을 해야 하는가"와 "어떤 지표를 어떻게 설계하는가"를 보여주는 것이 목적이다.

### 5-2. 분석용 OLTP 스키마

> **출처 구분**: 아래 스키마는 ERD(erdcloud)와 무관하게 **분석 목적으로 독자 설계**된 것이다.  
> 실제 배민 DB 구조와 다를 수 있으며, 포트폴리오 시뮬레이션용임을 명시한다.

#### orders
```sql
order_id              INT          -- 주문 고유 ID
restaurant_id         INT          -- 식당 FK
order_accepted_at     TIMESTAMP    -- 식당 주문 수락 시각
cooking_started_at    TIMESTAMP    -- 조리 시작 시각
pickup_ready_at       TIMESTAMP    -- 픽업 준비 완료 시각
order_type            VARCHAR      -- 한집 / 알뜰
is_converted_offline  BOOLEAN      -- 오프라인→온라인 전환 추정 (악천후 분석용)
created_at            TIMESTAMP    -- 주문 생성 시각
```

#### restaurants
```sql
restaurant_id    INT
category         VARCHAR     -- 한식 / 치킨 / 피자 / 분식
region           VARCHAR
avg_cooking_time INT         -- 평균 조리시간 (분)
max_capacity     INT         -- 동시 처리 가능 주문 수 (오버수락 측정 핵심)
```

#### deliveries
```sql
delivery_id      INT
order_id         INT
rider_id         INT
assigned_at      TIMESTAMP
pickup_at        TIMESTAMP
completed_at     TIMESTAMP
pickup_lat       FLOAT
pickup_lng       FLOAT
dropoff_lat      FLOAT
dropoff_lng      FLOAT
distance_km      FLOAT
is_rejected      BOOLEAN
rejection_reason VARCHAR     -- 거리 / 시간 / 날씨
```

#### riders
```sql
rider_id               INT
rider_type             VARCHAR  -- 자체 / 계약업체
consecutive_deliveries INT      -- 연속 배달 수 (피로도 proxy)
current_lat            FLOAT
current_lng            FLOAT
```

#### weather
```sql
weather_id        INT
recorded_at       TIMESTAMP
precipitation     FLOAT       -- 강수량 (mm)
wind_speed        FLOAT       -- 풍속 (m/s)
weather_grade     VARCHAR     -- 맑음 / 흐림 / 비 / 폭우 / 눈
is_adverse        BOOLEAN
demand_multiplier FLOAT       -- 평시 대비 주문량 배수
supply_multiplier FLOAT       -- 평시 대비 라이더 공급 배수
```

**테이블 관계**
```
restaurants 1:N orders
orders      1:1 deliveries
riders      1:N deliveries
weather     1:N deliveries  (recorded_at 시간 조인)
```

## 6. 분석 파이프라인

### 6-1. 7단계 파이프라인 + 브랜치 매핑

## 7. 데이터 마트 설계 (4개)

### 마트 간 관계

```
mart_kitchen_delay      ─┐
mart_rider_rejection    ─┼──▶ mart_eta_decomposition ──▶ Tableau 대시보드
mart_weather_supply_gap ─┘
```

mart_eta_decomposition은 나머지 3개 마트의 인사이트가 실제 ETA에 미치는 영향을 최종 통합한다.

---

### 마트 1: mart_kitchen_delay

| 항목 | 내용 |
|------|------|
| **목적** | Kitchen Delay 원인 분석 (가설 A/B 검증) |
| **Grain** | 식당 × 시간대 × 카테고리 |
| **핵심 지표** | Kitchen Wait Time, Slot Congestion Index, 오버수락률, 시간대별 주문 집중도 |
| **산출물** | "어떤 식당이, 어느 시간대에, 왜 밀리는가" 한 번에 파악 |
| **Tableau 연결** | 대시보드 1 (Kitchen Delay 현황) 직접 소스 |

**주요 지표 정의**

```
Kitchen Wait Time    = pickup_ready_at - order_accepted_at
Slot Congestion Index = 특정 시간 슬롯 내 해당 식당 주문 수
오버수락률           = 동시 진행 주문 수 / max_capacity  (> 1.0 이면 오버수락)
```

---

### 마트 2: mart_rider_rejection

| 항목 | 내용 |
|------|------|
| **목적** | 콜사 패턴 분석 + Dead Zone 탐지 |
| **Grain** | 라이더 × 완료 좌표(격자) × 배달 유형 |
| **핵심 지표** | 콜사율, Dead Zone 발생률, 거리별 콜사율, 라이더 유형별 콜사율, 피로도-콜사율 |
| **산출물** | folium Dead Zone 히트맵, 계약업체 vs 자체 라이더 콜사율 비교 |
| **Tableau 연결** | 대시보드 2 (배차 공백 현황) 직접 소스 |

**라이더 유형별 분석 → 계약업체 의존도 수치화**

```
계약업체 라이더 콜사율  vs  자체 라이더 콜사율
→ 격차가 크다면: 계약업체 의존도 리스크의 정량적 근거
```

> ⚠️ **검토 결과 — 순환논리 위험 (가장 중요한 결함)**  
> 시뮬레이션 단계에서 계약업체 라이더의 콜사율 파라미터를 높게 설정하면,  
> 그 데이터로 "계약업체가 더 자주 거절한다"를 검증하는 것은 순환논리다.  
> **해결 방향**:  
> ① 시뮬레이션에서는 두 라이더 유형의 파라미터를 **동일하게** 설정하거나,  
> ② 다양한 시나리오(격차 없음/있음)로 나누어 분석하고,  
> ③ 분석 섹션에서 "만약 실데이터에서 이 패턴이 관찰된다면" 으로 프레임을 전환한다.

---

### 마트 3: mart_weather_supply_gap

| 항목 | 내용 |
|------|------|
| **목적** | 악천후 수급 불균형 분석 + 프로모션 효과 검증 |
| **Grain** | 시간대 × 날씨 등급 × 지역 |
| **핵심 지표** | 수급 Gap, 날씨 등급별 콜사율, 프로모션 피처별 수락률 변화 |
| **산출물** | 수요↑ 공급↓ 구조를 수치로 증명, 프로모션 피처 중요도 |
| **Tableau 연결** | 대시보드 3 (악천후 대응 현황) 직접 소스 |

**수급 Gap 정의**

```
수급 Gap = (실제 주문 수 / 평시 평균) - (실제 라이더 공급 수 / 평시 평균)
         > 0: 수요 초과 (배차 압박)
```

---

### 마트 4: mart_eta_decomposition

| 항목 | 내용 |
|------|------|
| **목적** | ETA 전체 구성요소 분해 → 최종 KPI 모니터링 |
| **Grain** | 주문 단위 (가장 세분화된 Grain) |
| **핵심 지표** | Kitchen Wait Time + Pickup Wait Time + Last-mile Time = Total ETA |
| **산출물** | "어느 구간에서 얼마나 소요되는가" 분해 + 3개 마트 인사이트의 ETA 영향 최종 검증 |
| **Tableau 연결** | Executive Summary 대시보드 소스 |

**ETA 분해 공식**

```
Total ETA = Kitchen Wait Time
          + Pickup Wait Time   (픽업 준비 완료 ~ 라이더 픽업)
          + Last-mile Time     (픽업 ~ 배달 완료)
```

> 이 마트에서 Kitchen Delay 비중이 가장 크다는 것이 확인되면,  
> 마트 1의 심층 분석이 비로소 정당화된다.

### 핵심 지표 8개 선정 근거

| # | 지표명 | 원천 마트 | 선정 이유 |
|---|--------|---------|---------|
| ① | Kitchen Wait Time | mart_kitchen_delay | ETA의 핵심 구성요소, 분석 메인 타겟 |
| ② | Slot Congestion Index | mart_kitchen_delay | Kitchen Wait Time의 선행 지표 |
| ③ | 오버수락률 | mart_kitchen_delay | 가설 A 검증 핵심 |
| ④ | Pickup Wait Time | mart_eta_decomposition | Kitchen Wait Time의 결과 지표 |
| ⑤ | 콜사율 | mart_rider_rejection | 배차 공백 → ETA 직접 증가 |
| ⑥ | Dead Zone 발생률 | mart_rider_rejection | 콜사율의 선행 지표 |
| ⑦ | 수급 Gap | mart_weather_supply_gap | 악천후 ETA 폭등 직접 원인 |
| ⑧ | 피로도-콜사율 | mart_rider_rejection | 프로모션 피처, 라이더 공급 안정화 근거 |

**제외 지표 근거**

| 지표 | 제외 이유 |
|------|---------|
| Acceptance Delay | Kitchen Wait Time에 포함 (중복) |
| Total Delivery Time | 결과 지표 → 모니터링 용도, 분석 대상 아님 |
| 라이더별 평균 배달시간 | 부가 분석 → 우선순위 외 |

## 10. 논리 검토 및 한계 명시

### 10-1. 발견된 논리적 결함 및 해결 방향

| # | 결함 유형 | 내용 | 해결 방향 |
|---|---------|------|---------|
| **①** | **순환논리** | 시뮬레이션에서 계약업체 콜사율을 높게 설정 → 그 데이터로 "계약업체가 문제"를 검증하는 건 순환논리 | 라이더 유형 파라미터를 동일하게 설정하거나 다중 시나리오 분석. 결론은 "만약 실데이터에서 이 패턴이 나타난다면"으로 프레임 전환 |
| **②** | **검증 순서 역전** | Kitchen Delay가 ETA의 주된 원인이라고 전제하고 분석하는데, 이를 먼저 검증해야 함 | 파이프라인 4단계에 ETA 분해 배치 (mart_eta_decomposition을 선행 운영) |
| **③** | **임계값 근거 부재** | Slot Congestion Index의 "10분 슬롯", "N건 임계값" 근거 없음 | CS 경험 기반임을 명시 + 민감도 테스트(sensitivity test)로 임계값 변화 영향 확인 |
| **④** | **ERD-스키마 출처 혼용** | 학습용 ERD를 실제 배민 구조인 것처럼 오해할 소지 | ERD는 도메인 이해 목적 명시, 분석 스키마는 별도 설계 명시 (본 문서 2장/5장에서 이미 처리) |
| **⑤** | **외부 데이터 매핑 불완전** | 2장에서 언급한 외부 데이터가 어떤 파라미터를 뒷받침하는지 연결 고리 미흡 | 5장 시뮬레이션 파라미터 설정 시 각 수치의 근거 출처를 테이블 형태로 명시 |
| **⑥** | **콜사 가설 우선순위 미정** | 가설 A~D가 동시에 적용될 수 있어 "어느 요인이 더 중요한가" 판단 기준 없음 | EDA에서 각 요인별 콜사율 상관관계 탐색 → 피처 중요도 기반으로 우선순위 결정 |

### 10-2. 구조적 한계 (포트폴리오 레벨에서 명시할 내용)

1. **시뮬레이션 데이터의 근본 한계**: 파라미터를 어떻게 설정하느냐에 따라 결론이 달라질 수 있음. 포트폴리오의 목적이 "분석 구조 설계 능력"임을 명확히 하고, 인사이트는 "이런 패턴이 관찰된다면 이 의사결정을 할 수 있다"로 표현.

2. **Dead Zone 공간 분석의 현실성**: 실제 서울 지역 좌표 분포를 반영하기 위해 격자 기반 시뮬레이션이 필요하며, 단순 랜덤 좌표는 Dead Zone 분석의 신뢰도를 저하시킴. → folium 시각화 전에 서울 행정동 경계 데이터(공공데이터)를 활용해 현실적인 좌표 분포 구성 권장.

3. **계약업체 의존도 → 단일 지표 부재**: "계약업체 의존도"라는 구조적 문제는 정성적이며, 단일 수치로 요약하기 어려움. mart_rider_rejection의 라이더 유형별 비교를 복수 지표(콜사율, 피로도, 배달시간)로 보완해야 함.
