# 배달의 민족(Baemin) 데이터 분석 기획서

---

## 1. 프로젝트 개요

배달의 민족(Baemin)은 국내 최대 음식 배달 플랫폼으로, 고객(소비자), 가맹점(음식점), 라이더(배달원) 3자가 연결되는 O2O(Online to Offline) 비즈니스 구조입니다.

**분석 목표**: 배달의 민족 데이터를 수집·정제·분석하여 주문 최적화, 배달 효율화, 고객 이탈 분석 등의 비즈니스 인사이트를 도출

## 3. 도메인 핵심 엔터티 분석

배달의 민족 서비스의 핵심 주체(Subject)와 행위(Behavior)는 다음과 같이 정의됩니다.

- 주체(Subject/Source): 고객(User), 가맹점(Restaurant), 라이더(Rider), 메뉴(Menu)
- 행위(Behavior): 주문(Order), 결제(Payment), 배달(Delivery), 리뷰(Review), 쿠폰 사용(Coupon Usage)
- 대상(Object/Target): 음식(Food), 상품(Product)

---

## 4. 업무 관점의 데이터 테이블 종류 및 특성 분석

DW(Data Warehouse) 시스템 구축 시, 원천 시스템(기간계 시스템)의 테이블 종류와 그 특성을 올바르게 파악하는 것이 중요합니다. 이는 시계열 구축 여부, 이력 관리 전략, ETL 설계에 직접적인 영향을 미칩니다.

아래는 관계형 DB 이론이나 솔루션 관점이 아닌 업무(비즈니스) 관점의 테이블 분류입니다.

---

### 4-1. 원장성 테이블 (Master Table)

#### 개념 및 구성 형태
업무의 핵심 개체(Entity)들로서, 주로 행위의 **주체(Subject/Source)**에 대한 정보를 담고 있는 테이블입니다. 부속된 다수의 자식 테이블(Child Table)과 이력 테이블(History Table)을 수반합니다.

#### 데이터 성격
- **현재(최신) 상태 및 속성 정보**를 유지·관리
- **불변 속성**: 시간이 흘러도 변하지 않는 값 (예: 생년월일, 주민번호, 성별)
- **가변 속성**: 시간 경과에 따라 상태가 변하는 값 (예: 주소, 전화번호, 건강상태)
- 가변 속성 관리를 위해 **이력 테이블**이 반드시 부속됨

#### DW 구축 시 고려 사항
- 원장성 테이블은 **시계열(Time Serial)로 구축**되는 것이 원칙
- 기간계에 이력 테이블이 없거나 부실하면, DW에 새로 이력 테이블을 구축해야 함
- 스냅샷 이력(Snapshot History) 또는 선분이력(Line History) 방식 중 선택 필요

#### 배달의 민족 적용 예시

| 테이블명 | 설명 | 불변 속성 | 가변 속성 |
|----------|------|-----------|-----------|
| `user_master` | 고객 마스터 | 고객ID, 가입일, 소셜 계정 유형 | 배송지 주소, 연락처, 닉네임 |
| `restaurant_master` | 가맹점 마스터 | 사업자번호, 최초 등록일 | 영업 상태, 배달 가능 반경, 최소 주문금액 |
| `rider_master` | 라이더 마스터 | 라이더ID, 등록일 | 활동 지역, 배달 상태, 평점 |
| `menu_master` | 메뉴 마스터 | 메뉴ID, 가맹점ID | 가격, 메뉴 설명, 품절 여부, 이미지 |

> **예시 흐름**: "김민준 고객이 강남구 역삼동 맛집에서 치킨을 주문했다"
> - [김민준] → `user_master` (고객 원장성 테이블)
> - [맛집] → `restaurant_master` (가맹점 원장성 테이블)
> - [주문했다] → `order_transaction` (거래성 테이블)
> - [치킨] → `menu_master` (메뉴 원장성 테이블)

### 4-2. 거래성 테이블 (Transactional Table)

#### 개념 및 구성 형태
**행위(Behavior)**를 기록하는 테이블로, 특정 시점의 이벤트나 거래 내역을 저장합니다. 카드 거래 내역, 입출금 내역 등이 대표적인 예시입니다.

#### 데이터 성격
- **등록(INSERT)만 발생하며, 변경(UPDATE)이 원칙적으로 없는** 테이블
- 오류 정정 시에도 변경이 아닌 **취소 레코드를 신규 등록**하는 방식으로 처리
- 따라서 **이력 테이블이 존재하지 않음**

#### DW 구축 시 고려 사항
- **1:1 적재** 방식으로 DW에 가져오는 것이 원칙 (별도 이력 가공 불필요)
- 데이터 누적 구조이므로 파티셔닝 전략이 중요 (날짜 기준 Range Partition 권장)
- 주문 취소 처리 시 원본 레코드와 취소 레코드의 연결 관계 파악 필요

#### 배달의 민족 적용 예시

| 테이블명 | 설명 | 비고 |
|----------|------|------|
| `order_transaction` | 주문 거래 내역 | 주문 생성 시점 스냅샷, 취소는 별도 레코드 |
| `payment_transaction` | 결제 내역 | 결제수단(카드/포인트/쿠폰) 포함 |
| `delivery_log` | 배달 이벤트 로그 | 픽업 → 이동 → 완료 각 단계별 시간 기록 |
| `review_transaction` | 리뷰 등록 내역 | 작성 시점 기준, 수정 시 양면성 테이블로 전환 가능 |
| `push_notification_log` | 알림 발송 이력 | 마케팅/운영 알림 발송 이벤트 |

---

### 4-3. 양면성 테이블 (Duplicity Table)

#### 개념 및 구성 형태
거래성 테이블의 성격을 갖지만, 등록 이후 **수정(UPDATE)이 발생**하여 이력 테이블을 수반하는 테이블입니다. 예를 들어 카드 신청서처럼 "신청"이라는 행위의 정보를 저장하면서도 "신청 내용 수정"이 발생하는 경우입니다.

- **거래성 테이블의 성격**: 특정 행위(신청, 등록)의 정보를 저장
- **원장성 테이블의 성격**: 변경이 발생하며 이력 테이블을 수반

키 값(Key Value) 구성은 **행위 번호(예: 신청번호, 이벤트번호)** 기반이 됩니다.

#### 데이터 성격
- **최신 상태 정보를 유지**하되, 과거 변경 이력도 필요
- 기간계 설계 시 이력 테이블이 누락되는 경우가 많아 DW 구축 시 주의 필요

#### DW 구축 시 고려 사항
- 프로젝트 사이트 업무 환경에 따라 설계 방식이 달라짐
- 시계열 구축 필요 여부를 여러 각도로 검토 필요 (거래성 성격도 있어 데이터 크기가 큰 경우 多)
- 비효율적 설계 시 ETL 부하 및 적재 시간이 크게 증가
- 이력이 필요한 경우 주로 **점이력(Point History) 테이블**로 구축

#### 배달의 민족 적용 예시

| 테이블명 | 설명 | 양면성 이유 |
|----------|------|-------------|
| `restaurant_application` | 가맹점 입점 신청 | 입점 신청 후 서류 수정, 정보 보완이 빈번하게 발생 |
| `order_modify` | 주문 수정 내역 | 주문 확정 전 수량·옵션 변경 가능, 최종 상태 + 변경 이력 필요 |
| `coupon_issue` | 쿠폰 발행 내역 | 발행 후 조건 수정(유효기간, 사용처 변경) 가능성 |
| `rider_contract` | 라이더 계약 정보 | 계약 조건 변경이 주기적으로 발생 |
| `event_participation` | 이벤트 참여 신청 | 참여 후 정보 수정(참여 지역, 시간대 변경 등) 가능 |

---

### 4-4. 이력 테이블 (History Table)

#### 개념 및 구성 형태
**원장성 테이블의 가변 속성이 변경될 때** 이전 상태를 보관하는 역할을 합니다. 구성 형태에 따라 다음 3가지로 나뉩니다.

| 구분 | 설명 |
|------|------|
| **외부 이력 테이블** (Outer History Table) | 원장성 테이블 외부에 동일 구조로 분리 관리 |
| **내부 이력 테이블** (Inner History Table) | 원장성 테이블 내부에 상위 키(Upper Key) 포함, 재귀(Recursive) 구조 |
| **중요항목 이력 테이블** (Hot-Item History Table) | 핵심 상태 정보만 선별하여 이력 관리 |

#### 데이터 성격

이력 관리 방식은 크게 두 가지로 나뉩니다.

1) 선분이력 (Line History)
- 변경된 상태 정보를 **시작시점(start_dt) ~ 종료시점(end_dt)의 구간(선분)**으로 관리
- 주로 **원장성 테이블**에 구축
- 특정 시점의 상태를 조회할 때 유리
- 예: 가맹점 배달 가능 반경이 3km → 5km → 4km로 변경되는 과정을 구간으로 기록

2) 점이력 (Point History)
- **변경 시점(change_dt)** 기준으로 이력을 기록
- 주로 **양면성 테이블**에 구축
- 어느 시점에 어떤 변경이 발생했는지 추적하는 데 유리

#### DW 구축 시 고려 사항
- 기간계에 이력 테이블이 없으면 **DW에 스냅샷(Snapshot History) 이력**을 새로 구축
- 이력 방식 선택: 스냅샷 이력 vs 선분이력 vs 점이력 → 조회 패턴과 데이터 볼륨에 따라 결정
- 이력 테이블은 원장성 테이블과 **일관된 시계열 간격(일/월/년)**으로 관리

#### 배달의 민족 적용 예시

| 테이블명 | 이력 유형 | 설명 |
|----------|-----------|------|
| `user_address_history` | 선분이력 | 고객의 주 배송지 변경 이력 (start_dt, end_dt 관리) |
| `restaurant_status_history` | 선분이력 | 가맹점 영업 상태 변경 이력 (정상→정지→폐업) |
| `menu_price_history` | 점이력 | 메뉴 가격 변경 시점 및 변경 전/후 금액 기록 |
| `restaurant_application_history` | 점이력 | 가맹점 입점 신청 수정 이력 (양면성 테이블 연계) |
| `rider_grade_history` | 선분이력 | 라이더 등급 변경 이력 |

## 5. 테이블 종류 판별 기준 요약

DW 설계 시 원천 테이블의 종류를 올바르게 판별하기 위한 의사결정 흐름입니다.

1. 등록(INSERT)만 발생하는가?
   → YES: 거래성 테이블 (Transactional Table)
   → NO: 다음 단계로

2. 최신 상태를 유지하며 이력 테이블을 수반하는가?
   → YES: 원장성 테이블 (Master Table)
   → 일부만 YES (행위 기반 + 수정 발생): 양면성 테이블 (Duplicity Table)

3. 원장성/양면성 테이블에 부속되어 변경 이력을 보관하는가?
   → YES: 이력 테이블 (History Table)
      - 원장성 테이블 부속 → 선분이력(Line History) 고려
      - 양면성 테이블 부속 → 점이력(Point History) 고려

---

## 6. 분석 파이프라인 설계 방향

위 테이블 분류를 바탕으로 배달의 민족 DW/분석 파이프라인은 다음 방향으로 설계합니다.

1. **원장성 테이블** → 시계열로 적재 + 이력 테이블 구축 (없을 경우 DW에서 직접 생성)
2. **거래성 테이블** → 1:1 적재, 날짜 기준 파티셔닝 적용
3. **양면성 테이블** → 업무 환경 분석 후 시계열 여부 결정, 점이력 구축 우선 검토
4. **이력 테이블** → 선분이력/점이력 방식 확정 후 시계열 조회 최적화
